# OpenCode session_end falls back to session.deleted event subscription

## Context and Problem Statement

Canonical `session_end` (the `.events.json` hook that fires `team-levelup`) was silently dropped for OpenCode: `adlc-cli/src/registry.mjs` mapped `session_end` to `null`, so `resolveEvents()` skipped it and the generated hybrid plugin contained no `session_end` / `team-levelup` reference at all. OpenCode has no native session-end hook key in the plugin API, so a direct 1:1 mapping like the other agents' `SessionEnd`/`sessionEnd` was impossible. The decision was which OpenCode-native lifecycle signal should carry the canonical `session_end`, and with what execution semantics.

## Decision Drivers

* Parity: every other event-capable agent maps `session_end`; OpenCode must not silently drop it.
* Execution target: at session teardown there is no model context left to inject into — output has nowhere to go.
* Firing frequency: the fallback must run once per teardown, not repeatedly during the session.
* Stream safety: `session.deleted` and `file.edited` share the generic `event` handler namespace; the two streams must never mix.
* Minimalism: reuse the existing dispatcher contract (`node .agents/dispatcher.mjs <event> <skill> <dir> <timeout>` + `ADLC_EVENT` env) rather than inventing a new one.

## Considered Options

* Map `session_end` → `session.deleted` event subscription, dispatcher side-effect runners, output discarded (scripts only)
* Inject the skill body at teardown (body-injection path for `session_end`)
* Map `session_end` → `session.idle` instead

## Decision Outcome

Chosen option: "Map `session_end` → `session.deleted` event subscription, dispatcher side-effect runners, output discarded (scripts only)", because it is the only OpenCode-native signal that fires once per session teardown, and it works within the teardown reality that output has no injection target.

### Consequences

* Good, because `team-levelup` now actually fires at session teardown on OpenCode instead of being silently dropped — the deterministic script side-effect (e.g. Phase 0 setup resolving paths/`NEXT_CDR`) runs.
* Good, because the V1 generic `event` handler and the V2 `ctx.event.subscribe()` loop each type-guard on `session.deleted`, so `file.edited` nudges can never leak into the teardown path and vice versa.
* Good, because no new protocol was invented — the same dispatcher contract, timeout handling, and fail-open error behavior apply.
* Bad, because session-end runners are fire-and-forget: `team-levelup`'s full interactive CDR extraction/review/publish flow still requires an interactive `/team-levelup` run; the teardown hook cannot conduct multi-turn review.
* Bad, because of the silent-teardown-failure risk: if OpenCode ever changes the `session.deleted` delivery guarantee at plugin unload, the runner silently never fires. Mitigation: fail-open behavior is unchanged (same as the pre-fix state, but now the wired path is covered by regression tests that fail loudly in CI on any mapping/guard regression).
* Neutral, because `session.deleted` subscription requires the plugin host to deliver the teardown event before unloading; if OpenCode ever changes that lifecycle, the runner silently never fires (fail-open, same as before).

### Confirmation

Covered by the `session_end` regression tests in `adlc-cli/tests/events.test.mjs` (resolution mapping + V1/V2 handler generation + `event`-namespace guard separation) and the full `node --test` suite.

## Pros and Cons of the Options

### Map session_end → session.deleted event subscription, dispatcher side-effect runners, output discarded (scripts only)

Session teardown in OpenCode surfaces as the documented `session.deleted` event on the plugin event stream (`session.created/updated/deleted`, `session.idle`, `session.status`, …). Both plugin generations can observe it: V1 through the generic `event` handler, V2 through `ctx.event.subscribe()`. Running the dispatcher as a fire-and-forget side-effect fits because teardown output cannot be injected anywhere.

* Good, because it fires once per teardown — exactly the `session_end` semantic.
* Good, because both V1 (`server()`) and V2 (`setup()`) entrypoints are covered by the same canonical mapping.
* Bad, because the hook cannot return anything useful to the model — scripts only, body-injection path stays inapplicable for `session_end`.

### Inject the skill body at teardown (body-injection path for session_end)

Reuses the superpowers body path with no script needed.

* Good, because it needs no dispatcher execution at teardown — the body is static text.
* Bad, because there is no model request left to inject into at teardown, so the generated body would have nowhere to land.
* Risk: if the body path were enabled for `session_end`, output would be silently discarded on every agent, looking identical to the dropped-hook bug. Mitigation: `BODY_INJECTION_EVENTS` in both `src/registry.mjs` and `src/dispatcher.mjs` stays limited to `session_start`, `session_compact`, `user_prompt_submit` (already asserted by the "body injection applies to … only" test).

### Map session_end → session.idle instead

`session.idle` is documented alongside `session.deleted` and fires when a session goes quiet (e.g. the basis for "session completed" notification examples).

* Good, because `session.idle` may fire earlier and more reliably than deletion in some hosts, and earlier teardown work leaves more wall-clock for slow scripts.
* Bad, because idle fires on every idle transition — potentially many times per session — so `team-levelup` would rerun repeatedly mid-session instead of once at teardown, multiplying dispatcher load and risking duplicate side-effects.
* Risk: at-most-once teardown semantics would need deduplication state in the plugin. Mitigation: none implemented — rejected in favor of the fire-once `session.deleted` signal.
